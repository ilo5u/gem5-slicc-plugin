Get Started with SLICC / gem5 Ruby Language Support

Edit and explore gem5 Ruby cache-coherence protocols in CLion or IntelliJ IDEA. This plugin supports .sm and .slicc files; it is not a plugin for the Ruby programming language. The features described below are included in plugin version 1.4.0, prepared on 2026-10-21.

1. Install the Plugin

  1. Open your IDE's Settings → Plugins → Marketplace.
  2. Search for SLICC / gem5 Ruby Language Support and install an available version compatible with your IDE.
  3. Restart the IDE if prompted.

If you are testing a release that is not yet available on Marketplace, install its distribution ZIP using Settings → Plugins → Settings menu → Install Plugin from Disk. For a local 1.4.0 build, select build/distributions/slicc-plugin-1.4.0.zip. Select the plugin ZIP itself, not a source-code archive; do not extract it first.

Version 1.4.0 recognises all 30 gem5 SLICC reserved words, including global, wakeup_port, check_next_cycle, check_stop_slots, check_on_cache_probe, defer_enqueueing, and uppercase OOD. Attribute keywords in_trans, out_trans, and main work alongside interface and desc. Keywords are case-sensitive; use completion to discover them.

For the IDE's installation instructions, see Install and manage plugins.

2. Open Your Protocol Sources

  1. Open your gem5 source checkout or protocol source directory as an IDE project.
  2. Keep the protocol's .slicc root, included .sm files, and their relative include paths intact. Include shared interface declarations, such as RubySlicc_interfaces.slicc and its dependencies, in the project when available.
  3. Wait for project indexing to finish, then open a .sm or .slicc file. Syntax highlighting should activate automatically.

No separate language server or gem5 build is required for editor support. Cross-file assistance depends on the declarations and includes available in your project, so opening an isolated file may provide fewer results.

Rounded-square file icons distinguish .sm files with a blue SM badge and .slicc files with a purple H badge. Circular declaration badges use a/e/f/m/s/t for actions, enumerations, functions, machines, structures, and transitions. All icons have light/dark variants with font-independent lettering.

For external C++ type navigation, keep the Ruby Kconfig, SConscript, related build scripts, and C++ sources available. Prefer the complete gem5 checkout when common type headers live outside Ruby.

3. Try Completion and Parameter Information

  • Type a keyword or symbol prefix and invoke the IDE's Basic Completion action. Visible free functions include declarations from machine includes, protocol files, and global interfaces. For example, t or d can suggest tagLatency or dataLatency when those functions are declared in scope.
  • Type . after a variable whose type can be resolved to see its fields and member functions.
  • Type ( after a function name to see parameter information, or invoke Parameter Info with Ctrl+P. Overload signatures show the active argument position.

4. Navigate Between Actions, Functions, and Calls

Use Go to Declaration with Ctrl+B or Ctrl+Click on a name:

  • Transition → action: select an action reference in a transition body to open its implementation.
  • Action → transitions: select an action's declaration name to find the transitions that use it.
  • Function call or declaration → definition: open the matching SLICC definition, including definitions in included files. If there is no SLICC definition, a call opens the declaration instead.
  • Function definition → calling statements: select the function's definition name to find its calls inside functions and actions.
  • Declaration-only method → calling statements: select a method name in a structure or external_type declaration when no SLICC implementation exists. Free functions without definitions support this too.
  • Implicit action variable → type: use Ctrl+B or Ctrl+Click on implicit cache_entry inside an action to open the machine's primary AbstractCacheEntry implementation, such as Entry or CHI's CacheEntry. Omitted main defaults to true; main="false" excludes non-default types such as DirEntry. Implicit tbe opens TBE. Explicit function parameters and local variables take priority, and unrelated machine/include types are not selected.
  • Structure field → usage statements: select a field's declaration name in a structure to find reads, writes, and initializer uses. Matching follows the receiver's type and supported inheritance, and respects parameter/local shadowing.
  • Enum constant → usage statements: select a constant name in an enumeration or state_declaration to find its uses, including qualified constants and transition state/event references. Same-named constants from unrelated enums or machines are kept separate.

A single matching target opens directly. Multiple targets open a chooser. Function-call and member-usage candidates show the complete statement on one line with context, file, and line information; selecting one opens the actual identifier location. Distinct statements remain separate, while repeated uses within one statement share a candidate. Matching respects overload signatures and machine/include/type ownership.

5. Follow External Types into C++

  • Open a declaration such as structure(MessageBuffer, external="yes", ...) or external_type(MachineID) in a shared SLICC file.
  • Place the caret on the declared type name and use Ctrl+B or Ctrl+Click to open the matching reachable C++ definition or supported alias. For example, MessageBuffer opens its class in network/MessageBuffer.hh.
  • Ordinary type usages still navigate to their SLICC declaration. This feature does not navigate SLICC member functions or fields into individual C++ members.
  • Lookup follows supported literal Source / MakeInclude entries and transitive includes, including generated protocol-header forwarding. No prior gem5 build is required.

6. Use Message Variables in Their Scope

Without an explicit function parameter of the same name, message variables follow these implicit bindings:

  • Inside an existing peek(queue, MessageType) body, use in_msg. Type in_msg. for members of the second argument's message type.
  • Inside an existing enqueue(queue, MessageType) body, use out_msg. Type out_msg. for members of that message type.
  • Nested blocks inherit the surrounding bindings; an inner matching statement supplies the nearest binding. Usage outside the corresponding body is reported as an error.

Use queue and message-type names declared in your protocol; the names above illustrate the statement shape rather than a standalone protocol.

Explicit Message Parameters and Reference Parameters

An explicit function parameter named in_msg or out_msg takes priority throughout that function, including nested peek / enqueue bodies. Completion, references, navigation, and highlighting use the parameter's declared type rather than an implicit message binding. Without such a parameter, the message-body rules above still apply.

void prepareRequest(TBE tbe, CHIRequestType type, CHIRequestMsg & out_msg);
void functionalRead(Addr addr, Packet *pkt, WriteMask &mask);

Reference parameters such as out_msg and mask remain single declarations, regardless of spaces around &. Signatures and declaration/definition matching preserve reference and pointer modifiers; member lookup and supported call-result compatibility use the underlying SLICC type rather than C++ qualifier conversions. Implicit-type inlay hints do not repeat explicitly declared parameter types.

7. Explore the IDE Tools

  • Find Usages: Alt+F7 on a declaration.
  • Go to Symbol: Ctrl+Alt+Shift+N to search declarations by name.
  • Structure View: Alt+7 to browse machines, ports, actions, transitions, and functions.
  • Comments: Ctrl+/ for line comments and Ctrl+Shift+/ for block comments.
  • Colours: Settings → Editor → Color Scheme → SLICC (gem5 Ruby).

Shortcut examples use the default Windows/Linux keymap. If your platform or keymap differs, invoke the named IDE action or check its configured shortcut.

8. Optional: Adjust Call-Site Preview Length

Call-site labels show up to 160 Unicode characters by default, including an ellipsis when truncated. To use a different limit:

  1. Open Help → Edit Custom VM Options.
  2. Add the following as a separate line, preserving the existing options:
-Dslicc.navigation.maxStatementLength=240

Save the custom options and restart the IDE. This changes only the displayed preview length, not the source statement or navigation target. Remove the option to restore the default. Do not modify the IDE's bundled default VM options file. See Configure IDE JVM options for details.

9. Configure Parameter Name and Type Inlay Hints

  1. Open Settings → Editor → Inlay Hints → SLICC. Enable or disable Parameter names and Types independently.
  2. Open a resolved free-function or member-function call to see parameter names before its arguments. Unnamed parameters and arguments already named like their parameter do not receive hints. When overload resolution is ambiguous, only parameter names shared by all candidates are shown.
  3. Use implicit in_msg inside peek, out_msg inside enqueue, or tbe, cache_entry, and address inside an action. A type hint appears at the first actual use of each implicit binding; absent a matching explicit function parameter, nested message bindings take the nearest matching statement's second argument. Explicit visible variable declarations, including in_msg / out_msg parameters, are not annotated again.

Hints wait until project indexing finishes. They describe supported SLICC signatures and implicit bindings, not arbitrary C++ expression types.

10. Check Member Names

An unknown field or method name such as entry.nonexistent is underlined when entry resolves to a unique type with a complete visible SLICC interface hierarchy. Declared members, including those exposed by external="yes" structures and external_type, are accepted by name. The check respects inherited fields/methods, lexical shadowing, message scopes, reference/pointer parameters, and machine/include ownership.

The plugin does not search C++ classes for undeclared members or validate complete argument compatibility. Unknown types, missing/cyclic interfaces, ambiguous types, malformed declarations, indexing, and receivers whose type is not inferred intentionally receive no member error. This includes call results, parenthesized expressions, and indexed expressions. An unresolved chain element does not produce extra downstream errors.

11. Check Function-Result Types

The plugin checks function results assigned to declared variables or fields, including initializers, and function results used as arguments to other calls. For example, if getCount() returns int, bool ready := getCount() reports a mismatch on the result expression. A call such as consumeCount(getMessage()) is checked against the receiving parameter; using a void result as a value is also an error.

Inference covers simple variables, fields, nested free/member calls, and parentheses, respecting scopes and supported interface relationships. Overload candidates are selected from arguments, not the desired assignment type; candidates agreeing on the return type can still provide a definite result type. Reference/pointer call qualifiers are not treated as C++ conversion checks. Unknown expressions, ambiguous type declarations, conflicting overloads, malformed declarations, complex operators, indexed expressions, and indexing intentionally defer diagnostics. This does not validate every raw argument, function-body return statements, or complete C++ conversions. The member-name check remains separate.

12. Use Debug Flags and Format Diagnostics

Type DPRINTF( in an action to complete its first argument from literal DebugFlag / CompoundFlag declarations in related Ruby build sources. For example, DPRINTF(RubySlicc, "count=%d", count) takes a flag, format string, and values. DPRINTFN("count=%d", count) has no flag. A missing flag is an error; unknown-flag checks wait for sufficient source context.

Literal-format checks compare argument counts, not types. %% consumes no argument, and each star width/precision consumes one; nested-call commas are kept inside their argument. Dynamic/unsupported format strings and incomplete calls defer this check. APPEND_TRANSITION_COMMENT also has built-in parsing, highlighting, and completion. Attribute keywords block_on and format behave like main / desc; these additions do not change the 30 reserved words.

13. Check Transitions and Function Names

Missing action names in transition bodies and later duplicate state/event pairs are underlined after state/event sets and includes are expanded in machine order. Missing visible free and supported scoped function names are reported without confusing incompatible overload arguments with an absent function. Dot-member errors still use the separate type-aware member check. Ambiguous/incomplete scopes, unknown receiver types, and indexing defer checks that cannot produce a definite result.

14. Read Declaration Descriptions

Hover a declaration or scope-resolved usage, or invoke Quick Documentation with Ctrl+Q, to read its desc. Structures, fields, enumerations/constants, functions, and actions are supported. Matching function prototypes and definitions can provide each other's description. Text is HTML-escaped with line breaks preserved; a symbol with no description does not borrow text from its enclosing declaration.

Troubleshooting and Current Limits

  • No highlighting: confirm the plugin is enabled and the file is recognised as SLICC, rather than plain text or another file type.
  • Missing completion or navigation: check that the declaration, include targets, and relevant protocol files are present in the project and indexing has finished. Function names are not resolved by unrestricted same-name lookup across unrelated machines.
  • No reverse-navigation candidates: function-call search covers calls inside functions and actions; field/constant search also covers initializers and transition references. A function declaration with a matching definition opens that definition first; an unused declaration remains its own target.
  • Unresolved names: diagnostics are based on the plugin's available source declarations and supported resolution rules. They do not replace compiler diagnostics.
  • External C++ definition missing: check the declaration's external_name, its namespace, Source / MakeInclude entries, and reachable headers. A missing definition is an error; unavailable Ruby source context produces a warning. Lookup is static and considers conditional branches together, without executing Kconfig/SCons or preprocessing C++; computed paths and macro-generated definitions may not resolve.
  • Missing inlay hints: check the separate parameter-name/type controls under Settings → Editor → Inlay Hints → SLICC, and wait for indexing. Unresolved calls, conflicting overload parameter names, unnamed parameters, same-named arguments, and explicit visible variables may intentionally have no hint.
  • No member error: check that the receiver type and complete interface hierarchy are present and unambiguous, and that indexing has finished. This name-only check is deliberately conservative for unknown or incomplete declarations and unsupported receiver expressions.
  • No function-result error: check that the function, receiving variable/parameter, and supported expression types are visible and unambiguous. Complex expressions and incomplete or unknown types deliberately defer diagnostics; this check is limited SLICC type validation, not the compiler's full type system.
  • Rename refactoring, automatic formatting, and live templates are not implemented.

The plugin provides language-editing support. Build protocols and run simulations using your normal gem5 workflow.
