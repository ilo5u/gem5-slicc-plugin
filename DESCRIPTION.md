Language support for gem5 Ruby SLICC: highlighting, smart completion, cross-file navigation, and call-site discovery.

## Description
Read, write, and explore gem5 Ruby cache-coherence protocols in CLion and IntelliJ IDEA. SLICC / gem5 Ruby Language Support brings syntax and semantic highlighting, context-aware completion, parameter information, and source navigation to `.sm` and `.slicc` files.
Follow transitions to their actions, navigate between function declarations and definitions, and jump back to the exact statements that call a function. Follow external SLICC type declarations to reachable C++ definitions. Include-aware lookup and machine, member, and lexical scopes help distinguish similarly named symbols across protocol files. Inside `peek` and `enqueue`, message-variable types drive relevant member suggestions.
Built for developers and researchers working on the gem5 Ruby memory subsystem. This plugin supports the **SLICC protocol language**, not the Ruby programming language.

## Features
- **Syntax and semantic highlighting** — Distinguish SLICC keywords, types, machines, actions, functions, enumeration members, and fields. Customise colours in the IDE's SLICC colour scheme.
- **Complete reserved-word coverage** — Highlight and complete all 30 gem5 SLICC reserved words, including `global`, `wakeup_port`, `check_next_cycle`, `check_stop_slots`, `check_on_cache_probe`, `defer_enqueueing`, and case-sensitive `OOD`. Recognise `in_trans`, `out_trans`, and `main` as attribute keywords alongside `interface` and `desc`.
- **External SLICC types → C++ definitions** — Navigate from `structure` names marked `external="yes"` and `external_type` declaration names to reachable gem5 C++ type definitions and supported aliases. Respect namespaces, `external_name`, and Ruby source-root boundaries; report missing definitions as errors and unavailable source context as warnings.
- **Action ↔ transition navigation** — Jump from a transition's action reference to its implementation. From an action declaration, jump to its referencing transition or choose among multiple transitions.
- **Structure fields and enum constants → usages** — Select a structure field or enumeration constant declaration to find its concrete usage statements, including reads, writes, initializers, and state/event references in transitions. Jump to the actual usage with file/line context, distinguishing receiver types, inherited members, local shadowing, and machine/include ownership.
- **Function declaration → definition navigation** — Resolve calls and separate declarations to matching SLICC definitions, with overload-aware lookup across machine/include and member scopes.
- **Function → calling statements** — From a function definition, or a declaration without a SLICC implementation, find concrete calling statements in functions and actions. This also works for declaration-only `structure` and `external_type` methods.
- **Readable call-site previews** — Show complete multiline statements on one line, with caller, file, and line context. Jump directly for a single statement or choose among multiple statements, then navigate to the actual call. Previews have a configurable length limit, defaulting to 160 characters.
- **Include-aware function completion** — Suggest free functions from machine includes, protocol files, and global declarations, with return types and parameter signatures. Prefix completion includes functions such as `tagLatency` and `dataLatency` when their declarations are visible.
- **Type-aware member completion** — After `.`, show fields and member functions of the resolved receiver type, including supported `interface` inheritance chains. Handle chained accesses and comments around member-access operators.
- **Type-aware member error checking** — Flag unknown field and method names after `.` when the receiver type and its visible SLICC `interface` hierarchy are unambiguous and complete, including external declarations. Respect lexical shadowing, message scopes, reference/pointer parameters, and machine/include ownership; suppress downstream errors after an unresolved chain element.
- **Function-result type checking** — Check function results assigned to declared variables or fields, including initializers, and results passed as function arguments. Infer simple variables, fields, nested free/member calls, and parentheses within visible SLICC scopes; report definite nominal-type mismatches and invalid use of `void` results.
- **Scoped message variables** — Suggest implicit `in_msg` only in `peek` bodies and `out_msg` only in `enqueue` bodies. Infer their types from the second statement argument, respecting nested bindings, and flag out-of-scope usage. Explicit function parameters named `in_msg` or `out_msg` take priority throughout the function, including nested message blocks, and use their declared types for resolution, completion, navigation, and highlighting.
- **Function parameter information** — View overload signatures and the active argument with `Ctrl+P`, or automatically when typing `(` after a function name.
- **Reference parameters** — Recognise parameters such as `CHIRequestMsg & out_msg` and `WriteMask &mask` as single declarations. Preserve reference and pointer modifiers in displayed signatures and declaration/definition matching; use underlying SLICC types for member lookup and supported call-result compatibility.
- **Parameter name inlay hints** — Show parameter names before arguments of resolved free-function and member-function calls. Display hints for ambiguous overloads only where candidate names agree; omit unnamed parameters and arguments already named like their parameter.
- **Implicit type inlay hints** — Show the inferred type at the first actual use of each scoped `in_msg`, `out_msg`, `tbe`, `cache_entry`, or `address` binding, without repeating explicit visible variable declarations, including function parameters named `in_msg` or `out_msg`. Respect `peek` / `enqueue` message types and action scopes. Toggle parameter-name and type hints independently under Settings → Editor → Inlay Hints → SLICC; calculation waits until indexing finishes.
- **Scope-aware references and Find Usages** — Respect preceding local declarations, block visibility, and parameter/local shadowing. Distinguish resolved overloads and same-named symbols owned by different machines or types.
- **Protocol and global symbol lookup** — Follow protocol/include relationships and declarations exposed through `RubySlicc_interfaces.slicc` to navigate across source files.
- **Everyday editing tools** — Search symbols by name, browse the Structure View, fold declaration bodies, match braces, toggle comments, and highlight unresolved ordinary identifiers.

## Current Limitations
Rename refactoring, automatic code formatting, and live templates are not implemented. Member diagnostics check names exposed by SLICC declarations, not undeclared C++ members. Unknown receiver types, incomplete or cyclic interfaces, ambiguous types, malformed declarations, and indexing defer this name-only check; call-result, parenthesized, and indexed receivers are not inferred for member-name errors. Separate function-result checks use supported SLICC nominal types, not complete C++ conversions, validation of every raw argument, or function-body return-statement checking; unknown expressions, ambiguous type declarations, conflicting overloads, complex operators, and indexing defer these diagnostics. Inlay type hints cover implicit SLICC variables, not arbitrary C++ expressions. The plugin provides editor support; it does not replace the gem5 SLICC compiler or run simulations.

External-type lookup follows supported literal `Source` / `MakeInclude` / include paths, considering conditional branches together without executing Kconfig, SCons, or a C++ preprocessor. Computed paths and macro-generated definitions may not resolve. C++ member/call navigation is not included.
